# RTK installation and lifecycle for Codex

RTK compresses supported command output before an agent reads it. This guide
covers the standalone Ubuntu WSL installation used by Codex. Headroom's model
proxy and its bundled RTK remain separate, managed components.

## Installed baseline

On November 3, 2026, GitHub's latest-release API identified v1.1.0, published
October 25, 2026. The official v1.1.0 installer installed the Linux x86_64 musl
binary and verified its SHA-256 checksum against the release checksums.

| Component | Location and ownership |
| --- | --- |
| Standalone RTK 1.1.0 | `$HOME/.local/bin/rtk`; user-maintained upstream binary |
| Headroom RTK 0.48.0 | `$HOME/.local/share/Headroom/headroom/bin/rtk`; desktop-managed, retained unchanged |
| Codex hook | `$HOME/.codex/hooks.json`; one `PreToolUse` entry matching `Bash` |
| Hook command | `"/home/aaron/.local/bin/rtk" hook codex`; absolute path avoids inherited PATH ambiguity |
| Awareness document | `$HOME/.codex/RTK.md`; generated by the upstream initializer |
| Agent policy | `$HOME/.codex/AGENTS.md`; standalone routing and exact-output exceptions |
| Shell selection | User-owned `user:standalone_rtk` blocks after Headroom's blocks in `.bashrc` and `.profile` |
| Installation backup | `$HOME/.local/share/rtk/backups/20261103-codex-install`; private, outside Git |

The backup contains the original shell startup files, Codex hooks and agent
instructions, and a checksum of Headroom's binary. `RTK.md` did not exist before
installation. Existing GitKraken and Headroom hook entries were preserved exactly.
The initial installation did not change model-provider, proxy, or sandbox
permission settings. The later filesystem permission change is documented below.

## Install or upgrade

Run these steps in an ordinary WSL terminal with network access and write access
to the user's installation and configuration directories. First resolve the
latest stable release from the [upstream releases](https://github.com/rtk-ai/rtk/releases/latest)
and read its release notes. Do not assume the version recorded above remains latest.

Back up the current binary, `.bashrc`, `.profile`, and Codex `hooks.json`,
`AGENTS.md`, `RTK.md`, and `config.toml` before changing them. Use a new private backup directory
for each upgrade; do not overwrite the initial installation backup.

The maintainer's installer accepts an explicit release and installation directory.
For the qualified baseline:

```bash
rtk_install_dir="$(mktemp -d)"
curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/v1.1.0/install.sh \
    -o "$rtk_install_dir/install.sh"
# Inspect the downloaded installer before running it.
RTK_VERSION=v1.1.0 RTK_INSTALL_DIR="$HOME/.local/bin" \
    sh "$rtk_install_dir/install.sh"
"$HOME/.local/bin/rtk" --version
```

For an upgrade, replace both version references with the selected release. Keep
checksum verification enabled. Never install over Headroom's managed binary.

Initialize Codex explicitly; plain `rtk init -g` targets a different agent:

```bash
"$HOME/.local/bin/rtk" init --global --codex --dry-run
"$HOME/.local/bin/rtk" init --global --codex
```

The upstream initializer registers `rtk hook codex`, writes `RTK.md`, and adds
its reference to `AGENTS.md`. Global configuration uses `$CODEX_HOME` when set,
otherwise `$HOME/.codex`. Compare the result against the backup, preserving
unrelated hooks. Change only RTK's hook command to the absolute standalone path
shown in the table. Recheck this after every initializer run.

Headroom prepends its tools directory to PATH in both shell startup files.
Keep this user-owned block after that managed block in each file:

```bash
# >>> user:standalone_rtk >>>
# Prefer the standalone RTK over Headroom's bundled binary.
if [ -x "$HOME/.local/bin/rtk" ]; then
    export PATH="$HOME/.local/bin:$PATH"
fi
# <<< user:standalone_rtk <<<
```

Keep agent instructions pointed at the standalone executable. The former
Headroom RTK instruction block was replaced with a standalone policy, preserving
raw source reads, patch input, machine-readable evidence, hashes, and
`git diff --check`. The generated awareness document does not override these
exceptions. Use `rtk bypass COMMAND` when an automatic rewrite would filter
output that must remain exact. This bypass still tracks usage.

Restart Codex and its IDE backend after installation so hooks and PATH reload.
Review and trust the new hook if the client requests it.

## Verify operation

Check both login and interactive shells:

```bash
bash -lc 'command -v rtk; rtk --version'
bash -ic 'command -v rtk; rtk --version'
"$HOME/.local/bin/rtk" gain
```

Both shells must select `$HOME/.local/bin/rtk`. From a repository, compare a
native status result with RTK's compact result and verify raw bypass behavior:

```bash
"$HOME/.local/bin/rtk" git status --short
"$HOME/.local/bin/rtk" bypass git diff --check
```

Then ask a fresh Codex session to run `git status`. Inspect the actual tool call
and hook behavior. The maintainer documents the `Bash` matcher; do not infer
that shell calls nested inside `functions.exec` are intercepted.

November 3 qualification confirmed shell selection, binary version, preservation
of existing hooks, and a synthetic native hook response rewriting `git status`
to `rtk git status`. Synthetic `rtk bypass` source-read and whitespace-check
inputs were left unchanged. After the IDE reload, a plain `git status` through
`functions.exec` returned the same compact output as explicit RTK execution;
bypass returned Git's full output. Separate bypass checks preserved exact file
bytes and a deliberate exit code of 7. Recheck interception after client upgrades.

### History and sandbox access

RTK stores history in `$HOME/.local/share/rtk/history.db` by default on Linux.
SQLite needs write access to the containing directory for journal files as well
as the database itself. Compression can work while history recording fails with
`SQLITE_CANTOPEN`. Do not change file ownership or disable the sandbox to resolve
a missing directory grant.

In this IDE session, adding the initializer's suggested
`sandbox_workspace_write.writable_roots` setting did not add the directory to
the effective executor profile. A named permission profile resolved the issue.

#### Configure the filesystem profile

Back up the active Codex `config.toml` outside Git. For this installation it is
`$HOME/.codex/config.toml`; use `$CODEX_HOME/config.toml` if that variable is set.
Merge the following into the existing file, preserving unrelated settings:

```toml
# Top-level setting: place before any [table].
default_permissions = "workspace-rtk"

[permissions.workspace-rtk]
extends = ":workspace"

[permissions.workspace-rtk.filesystem]
"/home/aaron/.local/share/rtk" = "write"
```

The absolute path above is this workstation's tracking directory. On another
host, resolve the actual path first: `RTK_DB_PATH` overrides RTK's
`tracking.database_path`, which overrides the platform default. Grant the
dedicated parent directory, not the whole home directory.

The profile inherits the built-in workspace policy and adds RTK directory access.
Remove the older `sandbox_mode` and `[sandbox_workspace_write]` settings when
using named profiles: those older settings take precedence over
`default_permissions`. Review any existing legacy exceptions before migrating
them so required access is preserved. Do not create duplicate TOML keys or tables.

Reload the IDE, select **workspace-rtk** in the permissions control beneath the
composer, and start a new chat for verification. An existing chat can retain its
previous permission selection. A correct config file alone does not establish
that its profile is active.

#### Keep automatic approval review separate

The filesystem profile controls where commands can write. **Approve for me**
controls who reviews requests that cross the boundary. To configure automatic
review as the default, this workstation also has these top-level settings,
before any `[table]`:

```toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"
```

These settings do not grant additional filesystem or network access. Keep them
separate from the `[permissions.workspace-rtk]` table, and check the active chat's
approval selection after changing profiles.

#### Verify the effective permissions

Ask Codex to run the following inside its normal sandbox, without escalation:

```bash
rtk gain
```

Acceptance requires an effective write grant for the tracking directory and a
successful dashboard result without SQLite errors. If it fails, compare the
executor's actual permission profile with `config.toml`; a resumed chat or
client-supplied profile may still omit the directory. Success in an ordinary
terminal or escalated command does not establish sandbox access.

On November 3, 2026, the effective session profile included the RTK directory,
and `rtk gain` succeeded inside the sandbox with exit code 0 after the named
profile was selected. Its dashboard includes pre-existing history; it is not
an installation-only savings measurement. Private config backups were retained
beside `config.toml` before both permission and approval-default changes.

## Headroom updates and drift

After a Headroom update, RTK integration toggle, or connector repair, recheck:

- Shell selection and the ordering of the user-owned PATH blocks.
- Agent instructions for a regenerated `headroom:rtk` block naming the old binary.
- Exactly one standalone RTK hook, with its absolute executable path.
- The retained Headroom binary's version and ownership separately.
- The selected `workspace-rtk` profile and sandbox access to RTK history.

Headroom's setup state still records its RTK integration as enabled. Regeneration
of the edited files has not been tested. Keep the standalone configuration
explicit until Headroom supports the desired release and native Codex setup.
Do not disable Headroom's model proxy to resolve RTK command selection.

## Rollback and uninstall

For a binary-only rollback, restore the previously backed-up standalone binary,
verify its version, and restart Codex. If integration behavior changed, compare
the corresponding configuration backup and restore only RTK-related changes.
Do not overwrite unrelated configuration added since the backup.

To remove the standalone Codex integration, run its initializer before removing
the binary:

```bash
"$HOME/.local/bin/rtk" init --global --codex --uninstall
```

Review the result: remove the user-owned standalone PATH blocks and standalone
agent policy, and remove the standalone executable when no longer needed.
If returning to Headroom's bundled RTK, restore its previous routing block from
the backup and confirm the selected executable. Leave Headroom's managed binary,
model provider, and unrelated hooks intact. History and backups can be retained
for rollback; delete them only as a separate cleanup decision.

If also removing the RTK filesystem grant, select a different default profile
before deleting `permissions.workspace-rtk`. Preserve any other rules subsequently
added to that profile. Automatic approval-review defaults are independent of RTK
and can remain in place. Reload Codex and verify the resulting permissions.
